# 확장 설치

URL과 VSIX 설치, 패키지 저장소와 갤러리의 지원 범위는 이 페이지에 기록한다. 현재 공개된 API와 기여는 [확장 API](extension-api.md)에 있다. 폴더 URL 설치의 단계는 [확장 API의 URL에서 확장 설치](extension-api.md#url에서-확장-설치)에 있다.

## VSIX 설치

VSIX는 확장 하나를 담은 ZIP 파일이다. 확장의 파일은 `extension/` 아래에 있고 루트에 `extension.vsixmanifest`가 있다. 두 길로 설치한다.

- **Install from VSIX...**(`workbench.extensions.action.installVSIX`): 브라우저의 파일 선택 창에서 `.vsix` 하나를 고른다. 파일 선택 창은 커맨드를 실행한 사용자 동작에서만 열린다.
- **Install Extension from Location...**: 주소의 경로가 `.vsix`로 끝나면 그 파일을 내려받아 패키지로 설치한다. 그 밖의 주소는 지금처럼 폴더 URL이다. 주소 규칙은 폴더 URL과 같다(HTTPS 또는 `http://localhost`, `http://127.0.0.1`, 자격 증명 없음, 리다이렉트를 따라가지 않음, CORS 필요). 다운로드 링크에 필요한 쿼리는 남기고 `#` 뒤는 버린다.

설치 순서:

1. 패키지 바이트를 메모리에 받는다(50 MiB까지).
2. ZIP을 읽고 `extension/package.json`(256 KiB까지)만 푼다. 매니페스트 검증, `engines.vscode`가 `1.148.0`을 포함하는지, `extension.vsixmanifest`의 `TargetPlatform`이 없거나 `universal`, `web`인지, `browser` 진입 파일이 패키지에 있고 16 MiB 이하인지 본다. 하나라도 틀리면 무엇이 왜 틀렸는지 알리고 아무것도 쓰지 않는다.
3. 확인 화면(퀵 픽)이 표시 이름, 게시자, 버전, 식별자, 출처(파일 이름 또는 URL), 받은 크기, SHA-256, 서명 상태(VSIX는 늘 `unsigned`), `engines.vscode`의 호환, 경고를 보인다. 값은 모두 2에서 읽은 바로 그 바이트의 것이다. 확인한 뒤에 다시 내려받지 않는다.
4. **Cancel**이면 저장소에 아무것도 쓰지 않는다(임시 폴더도 만들지 않는다).

확인 화면의 선택지 이름:

| 이름 | 언제 |
| --- | --- |
| **Install** | 같은 식별자가 없을 때 |
| **Replace** | 같은 식별자의 다른 버전이 설치되어 있을 때. 새 버전을 설치하고 기록을 바꾼 뒤 옛 폴더를 지운다 |
| **Reinstall** | 같은 버전이 설치되어 있을 때. 같은 폴더를 새 내용으로 바꾼다 |
| **Install Contributions Only** | `browser`가 없는 패키지(`main`만 있는 데스크톱 확장). 기여만 적용되고 코드는 돌지 않는다 |

내장 확장과 같은 식별자는 거부한다. 폴더 URL 설치는 v0.1.0처럼 같은 식별자가 있으면 거부한다(먼저 제거한다). 같은 바이트를 설치 도중에 또 고르면 진행 중인 설치에 합친다.

### VSIX의 한도

| 무엇 | 한도 |
| --- | --- |
| 내려받기(파일 고르기 포함) | 50 MiB |
| 푼 합계 | 200 MiB |
| 항목 수 | 10,000 |
| 항목 하나 | 64 MiB |
| 항목 이름 | 512바이트(UTF-8) |
| `extension/package.json`, `extension.vsixmanifest` | 256 KiB |
| 패키지 진입 파일 | 16 MiB |

ZIP은 믿지 않는 입력으로 읽는다. 다음은 거부한다: 절대 경로, 드라이브 글자, 역슬래시, `..` 조각, 제어 문자, 정규화 뒤 같은 경로 둘(`a//b`와 `a/b`), 파일 경로가 다른 파일의 상위 폴더인 것, ZIP64, 분할 ZIP, 암호화, 저장(0)과 deflate(8) 말고의 압축 방식, 로컬 머리말과 중앙 디렉터리가 다른 항목, 서로 겹치는 항목, 잘린 파일, 틀린 CRC-32. 푼 바이트가 선언 크기나 한도를 넘는 순간 그 자리에서 멈춘다. 심볼릭 링크 항목은 설치하지 않고 경고로 보인다. 설치 대상은 `extension/` 아래 항목뿐이다.

### 지역화된 매니페스트 문자열

매니페스트에 `%키%` 값이 있으면 `package.nls.json`을 읽어 설치 기록의 `nls`에 넣는다(256 KiB까지). 폴더 URL 설치는 같은 이름의 파일을 그 폴더에서 받고, 없거나 읽지 못하면 넘어간다. `%키%` 값이 없는 매니페스트는 이 파일을 요청하지 않는다. 확인 화면과 제거 목록의 표시 이름은 이 문자열로 바꿔 보인다.

## 패키지 저장소

패키지 설치(VSIX, 나중에 Open VSX)는 파일을 브라우저 저장소(IndexedDB `writing-room-files`의 `vscode-userdata`)에 풀어 두고 거기서 실행한다. 설치한 뒤에는 네트워크 없이 새로고침해도 확장이 돈다.

- 패키지 폴더: `vscode-userdata:/extensions/<publisher>.<name>-<version>/`. 식별자는 소문자다. VSIX의 `extension/` 아래가 그대로 들어간다.
- 설치는 "임시 폴더(`/extensions/.tmp-<무작위>/`)에 풀기 → 모든 파일과 크기, `package.json`의 식별자·버전 확인 → 최종 이름으로 바꾸기(저장소 트랜잭션 하나) → 설치 목록 쓰기 → 확장 등록" 순서다. 어느 단계에서 실패해도 앞 단계를 되돌린다. 예외는 같은 버전의 **Reinstall**이다: 폴더를 새 내용으로 바꾼 뒤 등록이 실패하면 옛 기록으로 되돌리지 않고 새 파일과 맞는 새 기록을 남긴다. 확장은 다음 새로고침 때 등록된다. 한 탭 안의 설치와 제거는 기록·폴더·등록을 바꾸는 단계를 하나씩 차례로 한다. 탭이 중간에 닫혀도 기록이 있는 확장은 폴더가 있고, 기록에 없는 폴더는 확장으로 보이지 않는다.
- 제거는 "확장 등록 해제 → 확장 해제(`deactivate`는 최대 5초) 완료 대기 → 설치 목록 쓰기 → 패키지 폴더 지우기 → 확장 상태·비밀·저장 폴더 지우기" 순서다. 목록을 쓰지 못하면 확장을 다시 등록한다. 목록을 쓴 뒤 상태를 지우지 못하면 다시 등록하지 않고 오류만 알린다. 업데이트와 재설치는 옛 확장이 해제되는 동안 기존 기록과 패키지를 유지한다. 해제가 끝난 뒤 새 파일과 기록을 반영하고 새 확장을 등록한다.
- 워크벤치가 시작할 때 한 시간이 지난 임시 폴더와, 설치 목록에 없는 한 시간이 지난 패키지 폴더를 지운다. 한 시간이 안 된 것은 다른 탭에서 진행 중인 설치일 수 있어 남긴다. 검증에 실패한 기록이 가리키는 폴더도 기록에 있는 것으로 보고, 설치 목록 자체를 읽을 수 없으면 정리를 건너뛴다.
- 저장 공간이 모자라 풀기에 실패하면 임시 폴더를 지우고 필요한 바이트 수를 알린다.
- IndexedDB를 쓸 수 없는 창(차단, 일부 비공개 창)에서는 파일이 메모리에만 남는다. 확인 화면이 "Browser storage is unavailable: the extension stays for this session only."를 보인다. localStorage까지 쓸 수 없는 창에서는 지금 설치와 제거가 오류로 끝난다(wr-se1y).

### 설치 목록(스토리지 스키마 2)

설치 목록은 프로필 스토리지 키 `extensions.user`에 있다. 기록 하나의 필드:

| 필드 | 뜻 |
| --- | --- |
| `identifier`, `manifest`, `installedAt` | v0.1.0과 같다 |
| `source` | `location`(폴더 URL), `vsix`, `gallery` |
| `version` | 매니페스트의 버전과 같아야 한다 |
| `location` | `location`이면 폴더 URL, 그 밖이면 정확히 `vscode-userdata:/extensions/<식별자>-<버전>/` |
| `packageSha256`, `signature` | 패키지 출처에만. 소문자 16진 SHA-256, `verified`·`unsigned`·`unverifiable` |
| `galleryUrl` | `gallery`에만 |
| `nls` | 지역화된 매니페스트 문자열 |

읽는 쪽은 기록마다 검증하고 틀린 기록은 경고를 남기고 건너뛴다. 위치가 자기 패키지 폴더가 아닌 기록(다른 확장의 폴더, 워크스페이스, 사용자 데이터의 다른 자리)은 돌지 않는다.

`STORAGE_SCHEMA_VERSION`은 2다. 스키마 1의 기록(v0.1.0의 폴더 URL 설치)은 처음 열 때 `source: 'location'`과 `version`을 채워 변환한다. **되돌아갈 수 없다**: 변환한 브라우저를 v0.1.0으로 열면 v0.1.0은 더 새로운 스키마를 보고 그 세션을 메모리 저장으로 돌린다(저장된 값은 건드리지 않는다).

### 두 탭

설치 목록의 읽고 고쳐 쓰기는 Web Lock `writing-room:extensions.user`로 감싼다. 잠금 안에서는 그 탭의 캐시가 아니라 스토리지에 저장된 값을 읽으므로, 두 탭이 동시에 다른 확장을 설치해도 두 기록이 모두 남는다. 확인한 뒤 다른 탭이 같은 식별자의 기록을 바꿨으면 설치를 멈추고 다시 하라고 알린다. Web Locks가 없는 브라우저에서는 탭 안의 순서만 지킨다.

폴더 URL 설치는 풀 파일이 없어서 이 탭에 먼저 등록한 뒤 잠금 안에서 기록을 쓴다. 확인 화면이 닫히자마자 커맨드를 쓸 수 있고, 기록을 쓰지 못하면 등록을 푼다.

다른 탭에서 제거하거나 바꾼 확장은 이 탭에서 새로고침 전까지 돌 수 있다. 그 사이 그 확장의 파일 읽기(진입 파일, 아이콘)는 실패할 수 있고, 실패는 로그에 남을 뿐 페이지를 깨지 않는다.

### 저장한 자리에서 실행하기

- 진입 파일: 확장 호스트 Worker는 `vscode-userdata` 진입 파일을 메인 스레드에 요청한다(`MainThreadExtensionResources.$readPackageEntry`). 메인 스레드는 경로를 정규화한 뒤, 등록된 패키지 확장의 `browser` 진입 파일과 정확히 같을 때만 16 MiB까지 읽어 준다. 그 밖의 파일과 `..`로 벗어난 경로는 거부한다. 확장이 자기 폴더의 다른 파일을 `fetch`나 `Worker`로 쓰는 일은 런타임 영역의 일이다.
- 아이콘: 확장 아이콘, 커맨드의 아이콘(밝은·어두운 쌍 포함), 뷰 컨테이너 아이콘은 패키지 폴더 안에서 256 KiB까지 읽어 blob 주소로 보인다. `.png`, `.svg`, `.jpg`, `.jpeg`, `.gif`, `.webp`만 받는다. 실패하면 기본 아이콘이 남는다.

## 제거 목록

**Uninstall Extension...**의 항목은 `식별자 · 버전 · 출처`(`folder URL`, `VSIX`, `Open VSX`)를 보인다. 패키지 설치는 "Stored in this browser", 폴더 URL 설치는 그 오리진을 함께 보인다.

## 커맨드 아이콘

설치한 확장의 `contributes.commands`에는 codicon, 상대 경로 또는 밝은·어두운 테마용 `{ light, dark }` 경로 쌍이 들어갈 수 있다. 설치 매니페스트는 이 커맨드 정보를 메뉴 기여 지점으로 전달한다. 메뉴 기여 지점에서 확장 디렉터리 안의 경로인지 확인하고, 문제가 있는 아이콘을 빼고 커맨드를 등록한다. 경로 쌍의 두 값이 모두 유효해야 테마에 맞는 아이콘을 읽는다.

VSIX와 패키지 저장소도 이 계약을 따른다. 커맨드 아이콘은 메뉴 기여 지점에서 확인하고, 뷰 컨테이너 아이콘과 패키지 안의 파일 경로는 각 설치 검증에서 확인한다. URL 설치 후 다시 시작해도 같은 커맨드 정보를 읽는 동작은 `extension-foundation.spec.ts`에서 검증한다.

## Deviations from VS Code

- 패키지를 사용자 데이터의 IndexedDB에 풀고 확장 호스트가 메인 스레드를 거쳐 진입 파일을 읽는다. VS Code 웹은 갤러리의 리소스 URL에서 바로 실행한다 — 검증한 바이트와 실행하는 바이트가 같아야 해서다(wr-l3ch).
- 패키지 설치는 언제나 확인을 받고, 확인 화면이 받은 바이트의 크기와 SHA-256, 서명 상태를 보인다 — 확장 코드가 앱 오리진의 Worker에서 돌기 때문이다(wr-l3ch).
- 폴더 URL 설치는 같은 식별자가 있으면 거부하고, VSIX만 바꾸기와 다시 설치를 묻는다(wr-l3ch.9fi).
- 대소문자만 다른 ZIP 항목 이름은 다른 파일로 둔다. VS Code도 막지 않는다(wr-l3ch.285).
