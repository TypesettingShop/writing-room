# 입력을 보낸 뒤 폴링에서는 결과만 읽는다

## What happened

- 실제 Markdown 확장 인수 테스트에서 `markdown.occurrencesHighlight.enabled`를 바꾼 뒤 문서 하이라이트를 기다렸다. `expect.poll`은 상태를 읽을 때마다 `caretOn`을 불렀다. 이 도우미는 `Ctrl+Home`으로 문서 처음으로 간 다음 링크를 클릭한다.
- 링크를 클릭하고 약 12~20ms 뒤에 읽으면 하이라이트가 0이었다. 다음 시도까지 쉬는 사이에 하이라이트가 그려졌지만, 다음 시도의 `Ctrl+Home`이 다시 지웠다. `Ctrl+Home` 뒤 300ms를 기다리게 한 사본에서 수정 전 스펙은 dev와 preview 모두 켜기 대기의 20초 한도를 넘겼다.

## Why

- Monaco는 커서 이동 처리를 50ms 미룬다. 테스트 문서의 첫 자리에는 낱말이 없으므로, 커서가 거기에 머무르면 기존 하이라이트를 지운다. 링크에 커서를 옮긴 뒤에는 제공자 응답과 다음 프레임의 렌더링까지 기다려야 새 하이라이트를 읽을 수 있다.
- 첫 자리에서 링크까지 빠르게 이동하면 첫 자리의 처리가 실행되기 전에 다음 커서 이동이 들어온다. 링크에 이전 하이라이트가 남아 있으면 Monaco는 그것을 재사용한다. 설정 전환으로 제공자가 바뀐 뒤 새 요청을 확인하려면 이전 표시가 지워졌는지 먼저 확인해야 한다.

## Do this instead

1. 이전 결과를 새 결과로 읽을 수 있으면, 시도마다 이전 결과를 지우고 초기 상태를 확인한다. 이 테스트에서는 `Ctrl+Home` 뒤에 제공자 하이라이트와 텍스트 하이라이트의 합이 0인지 폴링한다.
2. 링크를 한 번 클릭한 뒤 커서를 그대로 둔다. `expect.poll`의 콜백에서는 원하는 종류의 하이라이트 개수만 읽는다. 설정을 켰다면 제공자 하이라이트 두 개 이상을, 껐다면 텍스트 하이라이트 하나 이상과 제공자 하이라이트 0개를 확인한다.
3. 입력을 다시 보내야 한다면 시도마다 관찰 시간을 주고, 시간이 지나도 조건을 만족하지 않을 때 첫 단계부터 반복한다. 전체 대기에는 상한을 둔다. 이 테스트의 `waitForLinkHighlights`는 상태를 읽는 폴링에 각각 3초, 시도 전체를 반복하는 `toPass`에 20초를 둔다.
4. 입력과 렌더링 사이가 벌어지는 조건에서 수정 전후를 비교한다. 같은 300ms 지연을 둔 사본에서 수정 후 dev와 preview 각각 2회 모두 켜기와 끄기 대기가 첫 시도에 통과했다.

[검사 대상 동작 직후의 상태와 이벤트를 확인한다](assert-effects-before-follow-up.md#do-this-instead)도 함께 읽는다.
