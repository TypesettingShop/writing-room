# 메모리 모드로 길을 가를 때는 작업이 실제로 닿는 저장소를 보고, 모드는 결정마다 다시 읽지 않는다

## What happened

- wr-uz4j가 스토리지의 메모리 모드(`IStorageService.usesMemory`)로 Web Lock과 `storeImmediately`를 건너뛰게 했다. 리뷰 wr-uz4j.lax가 세 자리를 찾았다.
- `ExtensionStorage.serialize`가 메모리 모드면 잠금을 건너뛰었는데, 같은 큐를 쓰는 `update`는 여전히 `storeImmediately`로 영속 백엔드를 다시 열어 쓴다. 메모리 모드 탭과 영속 탭이 같은 상태를 잠금 없이 덮어쓸 수 있었다(발견 1).
- `clear`가 `usesMemory`를 잠금 안에서 한 번(상태를 어떻게 지울지), 잠금 밖에서 한 번(저장 폴더를 지울지) 읽었다. 그 사이 물러서면 영속 상태는 지우고 폴더는 남겼다(발견 5).
- `commitPackage`가 폴더를 옮기기(`await packages.commit`) 전에만 모드를 보았다. 옮기는 동안 물러서면 세션에만 있는 기록이 영속 폴더를 가리켰다(발견 2).

## Why

- 메모리 모드는 작업 도중 아무 `await`에서나 참이 된다(다른 쓰기의 내려 쓰기 실패, storage 이벤트).
- "이 탭이 메모리 모드다"와 "이 작업이 영속 백엔드에 닿지 않는다"는 다른 말이다. `storeImmediately`는 메모리 모드에서도 백엔드를 다시 연다.

## Do this instead

- 잠금이나 영속 쓰기를 건너뛰는 조건은 서비스 전체의 모드가 아니라 그 작업이 실제로 부르는 저장 API로 정한다. 같은 큐를 쓰는 작업마다 따로 정한다(`serialize(task, inTabOnly)`처럼).
- 한 작업 안의 여러 결정(무엇을 지울지, 무엇을 남길지)은 모드를 한 번 읽은 값으로 한다.
- 되돌릴 수 없는 쓰기(기록 쓰기, 삭제) 바로 앞, `await` 없이 모드를 다시 본다. 앞의 확인은 그 사이의 `await`를 지나면 낡는다.
- 테스트는 작업 도중의 전환을 만든다: 확인 콜백이나 잠금 안에서 다른 키를 쓰고 내려 쓰기를 실패시킨다.
